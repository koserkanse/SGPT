# ADR-001: Continuous capability improvement

**Status:** Accepted; native instruction workflow implemented, executable adapters planned
**Date:** 2026-10-21
**Deciders:** SGPT owner

## Context

The owner wants SGPT to research open-source skills and plugins twice each week,
replace an existing implementation when an alternative works better, and carry
experience forward. The confirmed scope is Generative UI, agent infrastructure,
MCP integrations, persistent memory, document processing, sales/CRM,
presentations, and finance. Presentations and finance have the highest priority.

The existing fork has a CopilotKit workspace and an authenticated OpenDots bridge.
LibreChat also has GitHub skill synchronization and versioned skill management.
The evolution module now connects candidate discovery, comparative evaluation,
native instruction-skill activation, rollback and retained learning in one workflow.
Executable plugin and core-library deployment adapters remain on the roadmap.

Model and CopilotKit Intelligence credentials remain deferred at the owner's
request. The accompanying [program](program.yaml) remains the broader requirement
matrix. Runtime settings are loaded from `copilot.evolution` in `librechat.yaml`;
see [setup and implemented boundaries](../EVOLUTION.md). Enabling the feature
schedules research; missing model credentials prevent candidate activation.

## Decision

Use an application-owned improvement workflow with the eight versioned topics
defined in the program and runtime catalog. Research every topic twice weekly, processing presentations and
finance first. Monday and Thursday at 09:00 in Europe/Istanbul are proposed
defaults; the owner has specified the frequency, not these particular times.

Each run follows this lifecycle:

1. Discover candidates and updates from GitHub and official project sources.
2. Record repository, exact commit, package path, license, compatibility and
   dated source evidence. Discovery popularity is a shortlist signal only.
3. Compare the incumbent and candidates on the same versioned task fixtures,
   model/tool settings and resource budget. Include the owner's retained methods
   in both variants. Missing measurements mean unevaluated, never successful.
4. Promote a candidate automatically only when mandatory checks pass and the
   comparative task results improve without a mandatory regression. If nothing
   is better, retain the incumbent and record the research result.
5. Preserve the previous version and evaluation evidence. Verify after promotion;
   roll back a failed activation. Rollback restores implementation and bindings,
   while retaining the learning history and the reason for the rollback.
6. Show findings, evidence, active version, changes, failures, next run and rollback
   controls in SGPT's workspace. Report meaningful changes and actionable failures.

### Capability contracts

The registry identifies a capability by a stable topic/capability ID, independently
of its current implementation. It holds exact source versions, compatibility
contracts, evaluation suite version, activation receipts and previous bindings.

Adapters handle different update mechanisms:

- **Instruction skills:** stage a pinned source, evaluate it, and update the
  managed skill binding. Keep upstream contents and local learned methods
  separately so synchronization cannot overwrite local experience.
- **MCP services and plugins:** stage changes to the service/dependency
  configuration, run contract and integration tests, build and deploy the
  resulting version, then switch the binding after health verification.
- **Core libraries and agent infrastructure:** use an isolated Git branch and CI
  to produce a deployable change. A research recommendation or an opened PR is
  not an activated upgrade; the deployed revision must have a successful receipt.

Avoid assuming that unrelated plugins share an installation interface. Each
adapter must demonstrate install, health-check and restore behavior before it
can perform automatic promotion. Routine compatible upgrades need no new owner
approval; a new permission or unsupported migration remains a distinct action.

### Persistent learning

Store learned methods independently of package versions, scoped by owner/tenant
and capability. Each entry contains its source, supporting task/evaluation,
confidence, date, applicability and supersession history. Include preferences,
successful workflows, corrections, recurring failures and useful templates.

Research findings are candidate evidence. Validated task experience can become a
reusable method; discarded candidates still leave evidence explaining rejection.
Do not treat repository instructions as authority over the application's rules.
Do not copy a previous implementation's APIs blindly into a replacement.

On an upgrade, rebuild the active instructions from the new upstream skill and
applicable local methods, then rerun the evaluation suite. Corrections supersede
stale methods without deleting their history. This learning mechanism updates
retrievable knowledge and skills; model training is outside this initiative.

### Evaluation priorities

The [program](program.yaml) defines the initial checks for all eight topics.
Presentations must be assessed with actual editable artifacts and visual output;
a good-looking text outline alone does not demonstrate presentation ability.
Finance must use deterministic reference answers and workbook recalculation;
model self-assessment is not evidence of numerical correctness.

Use synthetic, reproducible fixtures initially. Add sanitized real failure cases
as regression fixtures as the system learns. Record fixture and evaluator versions
so scores from incompatible suites are not treated as comparable measurements.

## Options considered

| Option                                                        | Complexity | Benefit                                                           | Limitation                                                                   |
| ------------------------------------------------------------- | ---------- | ----------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| Follow a selected repository's latest version                 | Low        | Reuses GitHub synchronization                                     | Does not find or compare alternatives; can lose local changes                |
| Research and produce recommendations                          | Medium     | Provides evidence without integration adapters                    | Does not fulfill automatic replacement or apply retained methods             |
| Registry, comparative evaluations and adapter-based promotion | High       | Fulfills discovery, improvement, retained experience and rollback | Requires task fixtures and verified update adapters for each capability type |

## Trade-off analysis

Use the registry and evaluation approach. Reuse existing synchronization and
scheduling where their ownership and execution contracts fit. Keep the
improvement policy in SGPT rather than modifying the pinned OpenDots submodule.
OpenDots can supply conversations, research and learning integration; it does not
by itself establish that an alternative plugin improves SGPT's real tasks.

## Consequences

- The system can retain a proven implementation after an uneventful research run.
- Package changes no longer discard the owner's accumulated methods.
- Presentation and finance results have artifact-based acceptance criteria.
- Credentials, a continuously running host and functioning evaluation/deployment
  adapters are required before unattended execution can be considered active.
- Changing topic definitions or the evaluation suite invalidates comparable scores
  until the incumbent is measured again under the same conditions.
